# 强网杯报名材料交付清单

更新时间：2026-10-14

## 一、报名版统一定位

项目名称建议统一为：

> 忆安智护：面向智慧养老的护理数据安全治理与可信辅助决策平台

一句话主张：

> 系统把合成护理记录转化为可审计的安全决策、O-M-P-R 因果证据、来源可追溯的检索结果和跨存储删除验证；AI 只做辅助整理、检索和风险提示，不替代护工或医生。

比赛现场只讲一条主链：

```text
护理记录 -> ASDF/CASIA/PCCM-S -> O-M-P-R 因果证据
          -> 人工复核 -> 三存储写入 -> RRF 来源审计
          -> 隔离用户/会话跨存储删除验证
```

多模态、三维记忆、冷热分层和研究 Agent 作为“受控扩展”放在最后一页或答辩备份页，不作为主链正式指标。

## 二、现在必须优先完成的事项

### P0：锁定可录制主链

1. 固定 Docker 镜像、配置、演示账号、合成数据和浏览器地址。
2. 每次录制前运行 `docker compose up -d --build`、health check、fixture smoke 和 live smoke。
3. 视频中的每一个结果都来自服务端实际响应，显示 `trace_id`、阶段状态、来源状态和时间戳。
4. RRF 三路未通过 readiness 时，视频只能展示真实降级状态，不能把静态样例或历史 MRR 当成三路成功。
5. 删除演示必须使用专用评测用户/会话，并展示 dry-run、删除后计数、检索探针和幂等删除；未重跑成功前不在视频中宣称删除已完成。

### P0：清理材料中的失真表述

从报名版 PPT、策划书和旁白中删除或改写：

- “准确率 95%+”“因果无幻觉”“p95 小于 3 秒”（除非有冻结集和运行证据）；
- “机器遗忘”“参数级遗忘”“物理粉碎”；统一改为“隔离用户/会话跨存储删除验证”；
- “司法级不可篡改”“区块链存证”；改为“应用层审计哈希链和证据哈希”；
- “已完成 QLoRA/三路 RRF/多模态主链”；未通过对应门禁的能力标为“受控初步结果”或“受控扩展”；
- 旧路演稿中的融资额、客户数、GitHub Star、商业收入、性能承诺和虚构团队履历。

## 三、视频提交方案

建议成片 4-6 分钟，另保留一份 90 秒精简版。视频不使用长篇产品介绍，按以下顺序录制：

| 时间 | 画面 | 必须说清楚 |
| --- | --- | --- |
| 0:00-0:25 | 项目首页、真实运行模式标识 | 面向智慧养老护理数据治理，不替代医生/护工 |
| 0:25-1:05 | 护工输入一条合成护理记录 | 数据是合成或合法脱敏数据 |
| 1:05-1:45 | 安全判定卡片 | ASDF 归一化、CASIA 上下文、PCCM-S；展示命中层和 trace |
| 1:45-2:35 | 因果分析 | O-M-P-R 字段原文 span、否定/时序校验、模型层级、需要复核状态 |
| 2:35-3:10 | 医生人工复核 | 修改字段并提交队列；说明纠错不直接进入训练集 |
| 3:10-3:55 | 写入与检索 | 展示三存储状态、各路排名、RRF 分数和真实降级原因 |
| 3:55-4:35 | 删除验证 | dry-run、跨存储删除、探针、幂等和证明哈希；失败必须如实保留 |
| 4:35-5:00 | 证据摘要 | 数据集状态、已验证/受控初步/待完成三类证据边界 |

录制规范：

- 使用 `web/competition_console.html?mode=live`；模型或服务不可用时录制真实错误，不切换成伪造成功画面。
- 同时准备 `?mode=fixture` 作为网络故障备份，但画面必须醒目标记“离线夹具，不执行模型、联网、写入、检索和删除”。
- 屏幕中不得出现 `.env`、JWT、密码、GitHub PAT、数据库密码、真实护理原文或本机路径。
- 录制后保存原始视频、剪辑版、运行目录 JSON 和本次镜像/config 指纹，文件放在仓库外的提交材料目录。

## 四、PPT 报名版结构

建议 12 页以内：

1. 项目名称、场景与一句话价值。
2. 智慧养老护理数据的五个问题：碎片化、敏感、权限复杂、不可追溯、难删除。
3. 主链总览：安全判定 -> 因果证据 -> 检索审计 -> 删除验证。
4. ASDF/CASIA/PCCM-S：输入、决策、span、校准证据。
5. O-M-P-R：候选生成、模型裁决、证据校验、人工复核。
6. 三存储与 RRF：唯一 `doc_id`、来源排名、延迟和降级状态。
7. 删除验证：删除前后计数、探针、控制作用域保留、证明哈希。
8. 控制台和四角色权限：护工、医生、家属、老人。
9. 实验设计与对照组：安全、因果、RRF、删除、端到端。
10. 结果证据表：只列绑定 manifest/config/trace 的结果；其余明确标注受控初步或待完成。
11. 创新与边界：可审计、可解释、可撤回；不做诊断、不宣称参数级遗忘。
12. 现场演示流程、开源仓库和后续计划。

当前可以放入“受控初步结果”的数字：

- `test_data_400.json` 上 `asdf_casia_pccm` 检出 200/200、正常样本误伤 0/200；
- 该结果必须同时标注数据未经正式双人复核，不能写成冻结集正式成绩；
- 因果 Tuple F1、RRF MRR 提升和删除探针结果暂不写成达标成绩。

## 五、策划书源码版结构

策划书正文建议固定为：

1. 项目背景与目标用户。
2. 问题定义和合规边界。
3. 系统架构和主链流程。
4. ASDF/CASIA/PCCM-S 技术设计。
5. O-M-P-R 因果证据与人工复核。
6. 三存储/RRF 来源审计。
7. 跨存储删除验证证明。
8. 角色门户和现场控制台。
9. 实验协议、数据治理和统计指标。
10. 当前结果、失败结果和限制。
11. 受控扩展：多模态、记忆子图、冷热分层、研究 Agent。
12. 比赛演示和后续工作。

提交时同时保留：

- Markdown 源码：`docs/competition/项目策划书.md`；
- 版本化 DOCX：从 Markdown/模板重新生成，文件名带日期和版本号；
- 实验协议：`docs/competition/强网杯实验协议与证据门禁.md`；
- 证据目录索引：本清单、运行记录和正式 JSON/CSV/HTML 产物。

## 六、源码提交门禁

源码包只从 `context-keeper-main` 生成，不提交整个 `D:\context` 工作区。提交前执行：

```powershell
go mod verify
docker compose config --quiet
docker compose build context-keeper
python -m unittest discover -s experiments/scripts -p "test_*.py"
python -m unittest discover -s experiments/training -p "test_*.py"
python experiments/scripts/smoke_test.py --mode fixture
python experiments/scripts/release_guard.py
git diff --check
```

发布前必须完成：

- 所有源码改动已拆分提交，工作树中无未解释的临时文件；
- `.env`、令牌、模型权重、运行密钥、真实护理数据和个人信息均不在包内；
- `annotation_manifest_v1.json`、RRF readiness、删除验证和报告门禁状态与 PPT/策划书一致；
- 源码包能在干净 Docker 环境启动并打开控制台；
- 不使用历史对话中暴露的 GitHub PAT，公开仓库凭据采用新的最小权限短期令牌并在使用后撤销。

## 八、当前结论

项目已经具备参赛主链和可演示基础，但还不是“所有指标达标”的正式实验系统。报名材料应以“安全判定和证据治理链路已实现，部分大规模评测和扩展能力仍在受控验证中”为真实口径。临近截止时，稳定、可审计、可复现比继续增加页面或模型名称更重要。

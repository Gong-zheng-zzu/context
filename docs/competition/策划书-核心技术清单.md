## 🧠 一、智能记忆系统（核心竞争力）

### 1.1 多维度记忆检索引擎
**技术亮点：** 三维记忆检索架构（向量、图谱、时间线），结果来源可审计

#### 🔹 时间线记忆引擎（Timeline Engine）
- **技术栈：** 向量数据库 + 时间戳索引
- **核心能力：**
  - 按时间轴组织用户健康数据（体检报告、用药记录、症状变化）
  - 支持时间范围查询（"最近3个月的血压趋势"、"去年的体检结果"）
  - 自动识别时间相关查询并优化检索路径
  - 长期记忆永久保存，支持多年历史数据查询
- **应用场景：** 健康趋势分析、病情进展追踪、用药效果评估、历史对比
- **技术优势：** 基于向量数据库的时间戳过滤，支持灵活的时间范围查询

#### 🔹 知识图谱记忆引擎（Knowledge Graph Engine）
- **技术栈：** 实体向量存储 + 知识图谱混合检索
- **核心能力：**
  - 构建医疗实体关系网络（疾病-症状-药物-检查项目）
  - 支持概念推理（"高血压" → "心血管疾病" → "需要监测血脂"）
  - 多跳关系查询（"这个药和我之前吃的药有冲突吗？"）
- **应用场景：** 用药冲突检测、疾病关联分析、健康知识问答
- **技术优势：** 结合向量语义和图谱结构，并保留每路来源证据；融合收益以正式对比评测为准

#### 🔹 向量语义记忆引擎（Vector Engine）
- **技术栈：** Qdrant向量数据库 + nomic-embed-text嵌入模型
- **核心能力：**
  - 将对话和文档转换为高维向量（768维）
  - 语义相似度检索（"头晕" ≈ "眩晕" ≈ "头昏"）
  - 支持跨语言检索（中英文混合查询）
- **应用场景：** 模糊症状匹配、相似病例检索、智能问答
- **技术优势：** 突破关键词匹配限制，理解用户真实意图

### 1.2 智能检索策略引擎
**技术亮点：** LLM驱动的自适应检索策略

- **语义分析引擎（Semantic Analysis Engine）**
  - 自动识别查询意图（时间类/知识类/事实类）
  - 动态生成检索计划（选择最优引擎组合）
  - 查询改写和扩展（"血压高" → "高血压 OR 血压升高 OR 收缩压偏高"）

- **宽召回服务（Wide Recall Service）**
  - 并行调用三个检索引擎
  - 智能融合多源结果
  - 去重和质量评分

- **RRF 融合单元（`internal/services/rrf_fusion.go`）**
  - 生产主链路与评测通道**复用同一融合函数**，不再只在评测通道生效；参数由 `RRF_ENABLED` / `RRF_K` / `RRF_SOURCE_WEIGHTS` 配置，未配置时 K=60，来源权重 vector 1.0 / knowledge 1.2 / timeline 0.8
  - 审计字段保留：`rrf_score` / `rrf_sources` / `rrf_ranks` / `retrieval_fusion_mode` 等
  - 可选云端 cross-encoder 精排层（Cohere / OpenAI 兼容 rerank API），**默认关闭**，由 `RERANK_ENABLED` 等环境变量启用，失败时降级保留 RRF 排序并记录 `rerank_degraded`
  - 融合收益以正式对比评测为准

- **重排序服务（Reranker Service）**
  - 基于用户上下文重新排序检索结果
  - 考虑时效性、相关性、重要性三个维度
  - 支持 Top-k 结果审计；Top-3 指标以正式评测报告为准

### 1.3 记忆分层架构
**技术亮点：** 模拟人类记忆机制的三层存储

```
短期记忆（Short-term Memory）
├─ 当前会话的最近5-10条对话
├─ 存储位置：内存 + SessionStore
└─ 生命周期：会话结束后清除

长期记忆（Long-term Memory）
├─ 重要的健康档案（体检报告、诊断记录）
├─ 存储位置：向量数据库（永久保存）
└─ 生命周期：永久保存（用户可删除）

相关知识（Relevant Knowledge）
├─ 医疗知识库、用药指南、健康科普
├─ 存储位置：知识图谱 + 向量数据库
└─ 生命周期：系统预置 + 持续更新
```

## 🔒 二、隐私安全系统（医疗级数据保护）

### 2.1 身份认证与访问控制
**技术亮点：** JWT令牌认证 + 多租户数据隔离

#### 🔹 JWT身份认证（JSON Web Token）
- **技术栈：** golang-jwt/jwt + HS256签名算法
- **核心能力：**
  - 无状态认证：Token包含用户身份信息，无需服务器存储会话
  - 自动过期：24小时有效期，防止Token被长期滥用
  - 签名验证：防止Token被篡改或伪造
  - 双重隔离：UserID + WorkspaceID两层身份标识
- **安全特性：**
  - 密钥管理：从环境变量读取JWT_SECRET，生产环境强制配置
  - Bearer认证：标准HTTP Authorization头格式
  - 中间件保护：敏感API自动验证Token有效性
- **应用场景：** 用户登录、API访问控制、多租户隔离
- **技术优势：** 无状态设计，支持分布式部署，性能优于传统Session

#### 🔹 用户级数据隔离
- **技术栈：** UserID过滤 + 向量数据库Metadata
- **核心能力：**
  - 强制隔离：所有数据查询自动添加UserID过滤条件
  - 工作空间隔离：支持WorkspaceID二级隔离（家庭版/机构版）
  - 索引优化：用户索引加速查询，避免全表扫描
- **安全保障：**
  - 用户A无法访问用户B的数据（即使知道RecordID）
  - 向量检索自动过滤：Qdrant的Metadata过滤机制
  - 审计日志：记录所有跨用户访问尝试
- **合规性：** 符合《个人信息保护法》第51条（数据隔离要求）

### 2.2 数据加密存储
**技术亮点：** AES-256-GCM认证加密 + PBKDF2密钥派生

#### 🔹 AES-256-GCM加密算法
- **技术栈：** Go crypto/aes + cipher.GCM
- **核心能力：**
  - **AES-256**：256位密钥长度，业界最强对称加密标准
  - **GCM模式**：Galois/Counter Mode，认证加密（AEAD）
  - **完整性保护**：自动生成认证标签，防止密文被篡改
  - **随机化**：每次加密生成新的Nonce（12字节），防重放攻击
- **加密流程：**
  ```
  明文 → AES-256-GCM加密 → [Nonce(12字节) + 密文 + 认证标签(16字节)]
       → Base64编码 → 存储到数据库
  ```
- **解密流程：**
  ```
  Base64解码 → 提取Nonce → GCM解密+验证 → 明文
  （如果密文被篡改，验证失败，拒绝解密）
  ```
- **安全等级：** 使用标准 AEAD 认证加密；部署安全性取决于密钥管理和运行环境
- **性能指标：** 加密速度 >100MB/s，对用户体验无影响

#### 🔹 PBKDF2密钥派生
- **技术栈：** golang.org/x/crypto/pbkdf2 + SHA-256
- **核心能力：**
  - 密码派生密钥：从用户密码生成256位AES密钥
  - 迭代加固：100,000次迭代，防暴力破解
  - 盐值随机化：每个用户独立的16字节盐值
- **安全优势：**
  - 防彩虹表攻击：盐值随机化
  - 防暴力破解：使用可配置的高成本密钥派生参数，实际参数以部署配置为准
  - 符合NIST标准：NIST SP 800-132推荐方案
- **应用场景：** 健康档案加密、敏感字段保护、文件加密

#### 🔹 加密存储架构
- **加密范围：**
  - 健康档案内容（Content字段）
  - 敏感字段（病历号、诊断结果等）
  - 会话历史（对话记录）
- **密钥管理：**
  - 环境变量存储：ENCRYPTION_KEY（Base64编码）
  - 密钥轮换：支持定期更换密钥（重新加密）
  - 密钥隔离：用户级密钥（可选，增强隔离）
- **双重保险：**
  - 存储前加密：数据库中存储的是密文
  - 返回前脱敏：解密后再次脱敏敏感信息
- **合规性：** 符合《个人信息保护法》第51条（加密存储要求）

### 2.3 差分隐私保护（学术前沿技术）⭐⭐⭐⭐⭐
**技术亮点：** ε-差分隐私理论 + 拉普拉斯噪声机制

#### 🔹 什么是差分隐私？
差分隐私（Differential Privacy）是隐私保护的**数学理论**，由微软研究院Cynthia Dwork教授于2006年提出，被Google、Apple等公司用于数据收集。

**核心思想：** 通过添加数学噪声，保证即使攻击者知道数据库中其他所有人的信息，也无法推断出某个特定用户的信息。

**数学定义：** 一个算法M满足ε-差分隐私，当且仅当对于任意两个只相差一条记录的数据集D1和D2：
```
Pr[M(D1) ∈ S] ≤ e^ε × Pr[M(D2) ∈ S]


```
其中ε称为**隐私预算**，ε越小隐私保护越强。

#### 🔹 拉普拉斯噪声机制
- **技术栈：** math/rand + 拉普拉斯分布采样
- **核心能力：**
  - 向量噪声注入：向768维向量添加Lap(0, 1/ε)噪声
  - 归一化处理：保持向量在合理范围内（L2范数=1）
  - 可调隐私强度：通过ε参数控制隐私-效用平衡
- **数学模型：**
  ```
  噪声向量 = 原始向量 + Laplace(μ=0, b=1/ε)
  归一化后 = 噪声向量 / ||噪声向量||₂
  ```
- **隐私参数：**
  - ε = 1.0：强隐私保护（默认）
  - δ = 1e-5：失败概率（(ε,δ)-差分隐私）

#### 🔹 隐私预算管理
- **技术栈：** PrivacyBudgetManager + 时间窗口重置
- **核心能力：**
  - 全局预算控制：总预算限制（如ε_total = 10.0）
  - 用户级预算：每用户最多消耗总预算的10%
  - 自动重置：定期重置预算（如每24小时）
  - 预算追踪：记录每次查询消耗的隐私预算
- **安全保障：**
  - 预算耗尽时拒绝查询，防止隐私泄露累积
  - 用户级限制，防止单个用户耗尽全局预算
  - 审计日志，记录所有预算消耗

#### 🔹 应用场景
**场景1：用户数据删除保护**
- **问题：** 删除用户数据后，攻击者可能通过查询相似度反推原始数据
  - 例如：删除前查询"与用户A最相似的10个用户"得到结果R1
  - 删除后再次查询得到结果R2
  - 对比R1和R2的差异，可以推断用户A的数据特征
- **解决方案：** 删除前先用差分隐私混淆向量
  ```go
  // 1. 混淆向量
  obfuscatedVector := dp.ObfuscateVector(originalVector)
  // 2. 用混淆后的向量更新数据库
  updateVector(userID, obfuscatedVector)
  // 3. 再删除用户数据
  deleteUser(userID)
  ```
- **效果：** 攻击者无法通过相似度查询反推原始数据

**场景2：统计查询保护**
- **问题：** 聚合统计可能泄露个体信息
  - 例如："某养老院老人的平均血压"可能暴露某个老人的血压
- **解决方案：** 统计结果添加拉普拉斯噪声
  ```go
  trueAverage := calculateAverage(data)
  noise := dp.sampleLaplace(0, sensitivity/epsilon)
  noisyAverage := trueAverage + noise
  ```
- **效果：** 保护个体隐私的同时保持统计准确性

#### 🔹 技术优势
- **数学可证明**：隐私保护有严格的数学证明，不依赖攻击者的计算能力
- **组合性**：多次查询的隐私损失可以量化累加（隐私预算管理）
- **学术前沿**：Google、Apple、微软等公司在用的技术
- **跨领域创新**：将隐私计算理论应用于医疗AI领域

#### 🔹 学术价值
- **论文方向：** 《基于差分隐私的医疗AI数据保护方法研究》
- **研究边界：** 论文方向仅作为后续研究规划；当前实现不宣称达到任何会议发表水平
- **专利申请：** 一种基于差分隐私的用户数据删除方法
- **展示价值：** 可现场展示隐私预算与效用的权衡；不使用无法核验的参赛项目比例作比较

### 2.4 多层敏感信息检测 + 三大理论创新
**技术亮点：** 多层检测架构 + 三大项目内理论模型（原创性须经新颖性检索）

#### 🔹 检测层 1：正则表达式检测器（Regex Detector）｜对应 PCCM Layer 1
- **检测类型：** 30种医疗敏感信息
  - 身份证号、手机号、银行卡号
  - 医保卡号、病历号、就诊卡号、处方号
  - 血压、血糖、体温、心率等生理指标
  - API密钥、密码、Token
  - 邮箱、IP地址、URL
- **技术特点：** 规则路径可离线运行，延迟和准确率由评测脚本按数据集记录
- **准确率：** 待正式评测（按数据集、配置和清理流程留存证据）

#### 🔹 前置归一化：ASDF对抗样本防御框架（Adversarial Sample Defense Framework）
**定位：** 检测**之前**的归一化步骤，把绕过写法还原为标准形式；**本身不产出置信度、不参与 PCCM 融合**（实现见 `internal/security/asdf_framework.go` 的 `DefendAndNormalizeWithAudit`）。

**方法特点：** 借鉴AI安全领域的对抗样本归一化思想处理敏感信息绕过；未经新颖性检索不使用“首次”表述

- **核心思想：** 将绕过攻击视为"对抗样本"，通过检测-归一化-重检测三步策略防御
- **技术架构：**
  ```
  输入文本 → 对抗样本检测层 → 归一化层 → 标准检测层
  ```
- **支持的对抗样本类型：**
  - 空格分隔攻击：`1 1 0 1 0 1` → `110101`
  - 特殊字符混淆：`138-1234-5678` → `13812345678`
  - 同音字替换：`幺幺零幺零幺` → `110101`
  - 中文数字：`一一零一零一` → `110101`
  - Base64编码：`MTEwMTAx` → `110101`（解码）
- **防御成功率：** 待正式评测；现场展示归一化前后输入和检测审计记录
- **研究价值：** AI安全与隐私保护的交叉验证方向；论文或专利价值待检索、实验和评审

#### 🔹 置信度调整：CASIA上下文感知算法（Context-Aware Sensitive Information Algorithm）
**定位：** 作用于 PCCM Layer 1 / Layer 2 / Layer 4 的**置信度调整**，本身不构成独立的融合层（实现见 `internal/security/casia_algorithm.go`）。

**理论创新：** 解决"同一模式在不同上下文中含义不同"的误判问题

- **核心思想：** 通过分析上下文关键词，动态调整检测置信度
- **数学模型：**
  ```
  C_final = C_base × W_context
  W_context = 1 / (1 + e^(-Σw_i))
  ```
  其中 w_i 为上下文关键词权重（正权重增强，负权重抑制）
  
- **典型应用场景：**
  - 身份证 vs 邮编：`110101` 在"身份证"上下文中判定为敏感，在"邮编"上下文中判定为非敏感
  - 手机号 vs 工号：`13812345678` 在"联系方式"上下文中判定为敏感，在"员工编号"上下文中判定为非敏感
  - 病历号 vs 订单号：根据上下文关键词智能区分
  
- **技术优势：**
  - 误报率和准确率：待正式评测，按上下文标签和规则命中证据统计
  - 可解释性强：可追溯哪些上下文关键词影响了判定
  
- **研究价值：** 可形成上下文消融研究，是否具备发表价值待完整实验和同行评审
- **实现现状：** 关键词权重表已外置为 `config/casia_keywords.yaml`（默认与内置逐项一致）；已**具备**可选 embedding 语义匹配能力（接口注入式，**默认关闭**）：默认走精确关键词匹配（`MatchMethod = "exact"`，即 `strings.Contains`），仅显式注入相似度函数后才记为 `semantic`。默认路径未加载外部配置与校准产物，检测结果与改动前一致

#### 🔹 PCCM渐进式置信度累积模型（Progressive Confidence Cumulation Model）
**理论创新：** 多层检测结果的智能融合数学模型

- **核心思想：** 通过归一化加权平均与多层协同增强，将实际执行层的检测结果融合为最终置信度（实现见 `internal/security/pccm_model.go`）
- **数学模型：**
  ```
  C_final = (Σ wᵢ·Cᵢ / Σ wᵢ) × (1 + e·(n-1))，结果截断到 [0,1]
  ```
  其中：
  - Cᵢ：本次实际执行层的检测置信度 ∈ [0,1]；加权平均仅在置信度 > 0 的层上归一化，缺失信号不视为负证据
  - wᵢ：各层权重，权重之和无需为 1，模型内部做归一化
  - e：多层协同增强系数 `EnhancementPerExtraLayer`，默认 0.05
  - n：置信度超过层激活阈值 `LayerActivationThreshold`（默认 0.3）的层数；n = 1 时不增强
- **层结构（4 层）：** 默认权重 {1:0.70, 2:0.10, 4:0.15, 5:0.05}，对应 Layer 1 正则 / Layer 2 词典 / Layer 4 上下文规则 / Layer 5 LLM。Layer 3（NER）不参与执行，已从权重表移除。
- **实现归一：** `ProgressiveConfidenceModel` 是安全侧置信度融合的唯一真源，`multi_layer_detector.calculateConfidenceWithPCCM` 仅委托调用它；0.1 增强系数与 3 层结构属于已删除的历史实现。
  
- **技术特点：**
  - 渐进式检测：高置信度层可提前终止，计算开销由评测脚本实测
  - 权重校准：默认使用版本化固定配置（`CalibrationSource` 默认 `fixed_unvalidated`）；离线开发集校准流水线已跑出产物（开发集 100 条仓库自有标注样本、目标函数 `f1`、坐标下降 21 次评估），**未发现优于现有固定权重的配置**，权重保持 {1:0.70, 2:0.10, 4:0.15, 5:0.05}，来源标注为可追溯的 `devset_calibrated_v1`；校准产物需显式加载才生效，不声称在线自适应训练
  - 分层有效性与显著性（400 条四类别均衡样本，2026-09-20）：`asdf_casia_pccm` 检测率 **0.9200**（Wilson 95% [0.8740, 0.9502]），200 条良性样本误报率 0.0000（Wilson 上界 0.0188）。配对**精确** McNemar：`regex_only→asdf` **p=1.65e-24**（极显著）、`asdf→asdf_casia` **p=1.0**（该语料零效果）、`asdf_casia→pccm` **p=0.125**（**不显著**）。故 PCCM 层只主张「置信度建模与可追溯校准」，不主张检出率提升
  - 第三方数据集独立验证（同日，外部 6,677 条 `pii-bench-zh`，Apache-2.0）：`regex_only→asdf` 新增 212 条但**回退 162** 条（净 +50，p=0.0112），该缺陷在自建语料上未暴露；`asdf→asdf_casia` 再次 0/0、p=1.0；`asdf_casia→pccm` **+890、0 回退、p=2.42e-268**，召回 1.0000（Wilson [0.9994, 1.0000]）。**边界**：外部集为纯正样本，只测召回，不得与内部误报界合并陈述
  - 非线性增强：多层证据协同时按配置计算，增益由评测脚本实测
  
- **实验效果：**
  - 定量效果：待正式评测门禁通过后填写
  - 可解释性：每层置信度可追溯，便于审计
  
- **研究价值：** 可形成多层置信度校准研究，当前不作发表级别承诺

### 2.5 输出二次脱敏 + 九层安全过滤
**技术亮点：** 防止AI幻觉导致的信息泄露

#### 🔹 双重脱敏保护
- **输入脱敏：** 用户输入先经 ASDF 归一化，再进入正则 / 词典 / 上下文多层检测，并由 CASIA 调整上下文置信度
- **输出二次脱敏：** AI输出内容再次检测敏感信息
- **存储前脱敏：** 数据存储前第三次脱敏（双重保险）

#### 🔹 九层安全过滤（OutputFilter）
| 层级 | 过滤内容 | 示例 | 技术 |
|------|---------|------|------|
| 1️⃣ | 敏感信息检测 | 身份证、手机号、银行卡 | 复用多层检测引擎 |
| 2️⃣ | 黑名单关键词 | 系统路径、内网IP、凭证 | 关键词匹配 |
| 3️⃣ | SQL注入检测 | DROP TABLE, DELETE FROM | 正则模式匹配 |
| 4️⃣ | 内网IP过滤 | 192.168.x.x, 10.x.x.x | IP地址正则 |
| 5️⃣ | 系统路径过滤 | /etc/passwd, C:\Windows | 路径模式匹配 |
| 6️⃣ | Base64凭证 | 长度>60的Base64字符串 | 长度+模式检测 |
| 7️⃣ | 私钥内容 | -----BEGIN PRIVATE KEY----- | 私钥格式检测 |
| 8️⃣ | JWT令牌 | eyJ... 格式 | JWT模式匹配 |
| 9️⃣ | 环境变量泄露 | API_KEY=, SECRET= | 环境变量模式 |

#### 🔹 应用场景
- **防AI幻觉泄露：** AI可能"幻想"出不存在的敏感信息
- **防训练数据泄露：** AI可能输出训练数据中的敏感信息
- **防系统信息泄露：** 防止AI输出系统路径、内网IP等
- **防凭证泄露：** 防止AI输出密码、密钥、Token等

#### 🔹 技术优势
- **纵深防御：** 输入+输出双重脱敏，全链路保护
- **全面覆盖：** 医疗敏感信息+系统安全信息
- **智能过滤：** 根据上下文判断是否过滤
- **可追溯：** 所有过滤操作记录日志

## 🌟 七、技术创新点总结

### 7.1 核心创新（三大理论创新 + 三大隐私技术 + 工程创新）

#### 🏆 项目内算法设计（原创性须经新颖性检索）

1. **PCCM - 渐进式置信度累积模型**
   - 提出多层检测的置信度融合数学模型
   - 引入非线性增强因子，体现多层协同效应
   - 当前使用版本化固定权重；离线开发集校准流水线已建立，产物需显式加载才生效，不声称运行时自适应训练
   - **研究价值：** 可开展消融与校准研究；论文或专利价值待外部评审
   - **实验数据：** 待正式评测门禁通过后填写

2. **CASIA - 上下文感知的敏感信息识别算法**
   - 解决"同一模式在不同上下文中含义不同"的问题
   - 提出上下文关键词权重表和sigmoid归一化方法
   - 引入正负权重机制（正权重增强，负权重抑制）
   - **研究价值：** 可开展上下文证据消融研究，当前不作发表级别承诺
   - **实验数据：** 待正式评测门禁通过后填写

3. **ASDF - 对抗样本防御框架**
   - 借鉴对抗样本归一化思想处理敏感信息绕过，不主张未经检索验证的首次性
   - 提出"检测-归一化-重检测"三步防御策略
   - 可扩展的检测器架构，易于添加新的对抗样本类型
   - **研究价值：** AI安全与隐私保护的交叉工程验证，发表或专利价值待检索与评审
   - **实验数据：** 待正式评测门禁通过后填写；现场可展示归一化样例

#### 🔐 隐私保护创新（学术前沿技术）

4. **差分隐私保护（Differential Privacy）**
   - 基于ε-差分隐私理论，添加拉普拉斯噪声
   - 隐私预算管理：全局预算+用户级预算双重控制
   - 应用场景：用户数据删除保护、统计查询保护
   - **学术价值：** Google、Apple等公司使用的前沿技术
   - **技术边界：** 使用标准差分隐私机制；实现质量以隐私预算、威胁模型和测试证据为准，不以学历或会议级别包装
   - **展示价值：** 现场呈现隐私预算与统计效用，不使用无法核验的同类项目比例

5. **AES-256-GCM认证加密**
   - 业界最强对称加密标准（256位密钥）
   - GCM模式提供认证加密（AEAD），防篡改
   - PBKDF2密钥派生（100,000次迭代），防暴力破解
   - **安全等级：** 使用标准 AEAD 方案；具体安全等级须结合密钥管理和部署环境评估
   - **合规性：** 符合《个人信息保护法》第51条

6. **输出二次脱敏 + 九层安全过滤**
   - 防止AI幻觉导致的信息泄露
   - 九层过滤：敏感信息+系统路径+SQL注入+凭证+私钥+JWT等
   - 纵深防御：输入脱敏+输出二次脱敏+存储前脱敏
   - **技术深度：** 远超一般项目（通常只有输入脱敏）

#### 🔧 工程创新

7. **三维记忆检索架构**

### 8.3 安全技术
- **加密：** AES-256-GCM（认证加密）
- **密钥派生：** PBKDF2（100,000次迭代）
- **认证：** JWT（HS256签名）
- **传输：** HTTPS/TLS 1.3
- **脱敏：** 正则 + ASDF + CASIA + 九层输出过滤
- **隐私保护：** 差分隐私（ε=1.0）

### 8.4 部署技术
- **容器化：** Docker（可选）
- **操作系统：** Windows/Linux/macOS
- **最低配置：** 8GB内存 + 20GB硬盘

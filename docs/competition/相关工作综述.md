# 相关工作综述

> 本文件为项目中文敏感信息检测系统的「相关工作」对比综述，用于支撑对比实验定位与创新点说明，**不作为发表级文献综述**。全部结论基于公开检索（GitHub / Hugging Face / ScienceDirect 等页面与论文摘要），**未逐篇精读全文**，不确定的细节宁可省略，不虚构文献内容。

## 一、引言

中文敏感信息（PII / PHI，个人身份信息 / 受保护健康信息）检测是隐私保护与数据治理的基础环节。与英文场景相比，中文 PII 检测面临几类特有的挑战：

- **形态多样**：身份证号、手机号、银行卡号、护照号、邮箱等各有一套编码规则，且常以带校验位、带区号、带分隔符的形态出现；
- **对抗与混淆**：真实数据中常见以空格、特殊字符、同音字、中文数字、Base64 等方式对敏感值进行混淆，绕过基于「标准形态」的检测；
- **上下文歧义**：同一数字形态在不同语境下含义不同——「110101」既可能是身份证前六位，也可能是邮政编码；「18 位数字」可能是身份证号，也可能是订单号、快递单号、发票号等非敏感编号；
- **标注与评测受限**：真实 PII 受法律保护，公开评测多采用合成或脱敏数据，难以获得大规模、真实分布的人工标注语料。

现有方案大体可归为两类：**基于规则与命名实体识别（NER）的基线**，与**基于大语言模型（LLM）的方法**。下文分节梳理，并据此说明本项目的定位。

## 二、规则与 NER 基线

### 1. Microsoft Presidio

- **标题**：Microsoft Presidio（开源 PII 去标识化框架）
- **来源**：GitHub（Microsoft）
- **要点**：以「规则 + 模型」相结合的方式识别 PII。内置针对手机号、邮箱、信用卡号、姓名、地址等实体的识别器，支持多语言，是当前中文 PII 脱敏方案最常借用的底层框架。

### 2. cn_pii_anonymization

- **标题**：cn_pii_anonymization（中文 PII 匿名化库）
- **来源**：GitHub（neednlab，MIT 许可）
- **要点**：基于 Microsoft Presidio 框架的中文 PII 脱敏库。纯正则识别手机号、身份证号、银行卡号、护照号、邮箱（置信度 1.0），并借助 PaddleNLP 信息抽取识别姓名、地址（置信度约 0.3–0.6）。**特点是「纯规则 + NER」：无上下文感知的负向抑制，也无对抗样本归一化**，对混淆样本与语境歧义样本无能为力。

### 3. 两阶段匿名化框架（fine-tuned BERT）

- **标题**：两阶段匿名化框架（基于 fine-tuned BERT 的实体检测）
- **来源**：ScienceDirect
- **要点**：用微调后的 BERT 检测姓名、日期、地点等实体，据页面/摘要所述在相应数据集上 F1 超过 90%。属于「纯模型」方法——依赖实体类型标签，不感知「同一形态在不同语境下是否敏感」的语义差异。

### 4. 知识驱动 + 数据驱动结合的去标识化（两遍标注）

- **标题**：知识驱动与数据驱动结合的去标识化方法
- **来源**：JBI
- **要点**：采用「两遍标注」方法提升 PHI 实体识别效果，据称与人工基准相当。体现的是「提升实体识别的精度」，关注点仍在实体边界识别本身，而非上下文抑制或对抗还原。

## 三、LLM 方法与商业工具

### 5. 中英混合临床文本去标识化（LLM 方法）

- **标题**：中英混合临床文本的 PHI 去标识化
- **来源**：ScienceDirect
- **要点**：用大语言模型对中英混合临床文本做 PHI 去标识化。LLM 方法可借助语义理解覆盖「只描述敏感值而不含其字面形态」的场景（如「手机号是 170 开头的十一位号码」），但存在输出不确定、不可复现、可能引入误报的固有代价。

### 6. 商业 / 开源 PII 检测工具（Azure PII / AWS Comprehend PII）

- **标题**：Azure AI Language PII、AWS Comprehend PII 等
- **来源**：微软 / AWS 官方文档
- **要点**：与 Presidio 同属「规则 + 模型」路线。公开评测普遍使用**合成或脱敏数据**（真实 PII 受法律保护），因此其公开指标难以直接迁移到真实中文对抗场景。

### 7. 去标识化系统综述

- **标题**：去标识化系统综述
- **来源**：ScienceDirect
- **要点**：指出**现成工具在特定 PHI 类型（如职业）上效果差**，往往需要针对具体领域适配，而适配本身有额外成本。这一结论与本项目「针对中文易混淆/易对抗场景做专门设计」的出发点一致。

### 8. 中文 PII 检测基准数据集

- **标题**：pii-bench-zh（中文 PII 检测基准）
- **来源**：Hugging Face
- **要点**：中文 PII 检测基准数据集，含 formal 与 chat 两个子集，提供模板化合成样本与实体标签。本项目已将其用于外部独立验证（Apache-2.0 许可，见《对比实验报告.md》）。

## 四、现有方法的局限与本项目定位

综合上述调研，现有基线可归纳为「纯规则」或「纯模型」两条路线，它们各自存在三类**结构性空白**：

1. **缺乏上下文感知的负向抑制**。规则/NER 基线看到「身份证形状」就判敏感，无法区分「身份证号」与「订单号里的 18 位数字」「工号里的 11 位手机号形状」这类语境否定的情况，导致形状误报。cn_pii_anonymization 与两阶段 BERT 框架均不具备这一能力。

2. **缺乏对抗样本归一化**。规则/NER 基线依赖「标准形态」，对空格分隔（`1 1 0 1 0 1`）、特殊字符（`138-1234-5678`）、同音字（`幺幺零幺零幺`）、中文数字（`一一零一零一`）、Base64（`MTEwMTAx`）等混淆形态无法还原，召回受限。

3. **缺乏多算法渐进置信度融合**。单一路线（规则或模型）各自给出「命中/不命中」的二元或单点判断，缺少把「正则、词典、上下文规则、LLM」等多层证据按权重渐进累积、并给出可审计置信度的统一机制。

本项目提出的三个核心组件（CASIA、ASDF、PCCM，详见《核心创新点总结.md》）正是针对这三处空白：

- **CASIA（Context-Aware Sensitive Information Algorithm，上下文感知敏感信息算法）**：通过上下文关键词正/负权重 + sigmoid 归一化，把「订单号里的身份证形状」「工号里的手机号形状」等语境否定样本**负向抑制**为非敏感，填补空白 (1)。
- **ASDF（Adversarial Sample Defense Framework，对抗样本防御框架）**：以「检测—归一化—重检测」三步策略，还原被空格、特殊字符、同音字、中文数字、Base64 混淆的敏感值，填补空白 (2)。
- **PCCM（Progressive Confidence Cumulation Model，渐进式置信度累积模型）**：对正则、词典、上下文规则、LLM 等多层证据做加权累积与非线性增强，输出统一、可审计的置信度，填补空白 (3)；叠加 LLM 兜底覆盖「语义指代」这一确定性链路的结构性边界。

> 需要如实说明的边界：CASIA / ASDF / PCCM 是项目内的工程命名与组合设计。ASDF 借鉴对抗样本归一化思想用于敏感信息绕过检测；项目答辩只主张可由代码、消融与审计证据验证的设计，**不主张未经文献与专利检索证明的首次性**。三者的定量贡献（检测率、误报率、显著性）以《对比实验报告.md》中通过门禁的正式评测为准，本文不重复罗列数字。

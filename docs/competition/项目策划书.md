# Context-Keeper 项目策划书

## 📋 项目概述

### 项目名称
**Context-Keeper** - 智能上下文记忆管理系统

### 项目定位
面向企业级 AI 应用的智能记忆与上下文管理中间件，解决大语言模型（LLM）应用中的上下文持久化、跨会话记忆、敏感信息保护等核心问题。

### 核心价值主张
> "让 AI 拥有记忆，让对话更智能"

---

## 🎯 市场背景与痛点分析

### 1. 市场背景

#### 1.1 AI 应用爆发式增长
- 2024-2026年，企业级 AI 应用市场年增长率超过 150%
- ChatGPT、Claude、文心一言等大模型广泛应用
- 企业对 AI 助手的需求从"能用"转向"好用"

#### 1.2 上下文管理成为瓶颈
- **LLM 上下文窗口限制**：即使最新的模型（如 Claude 4），上下文窗口也有限制
- **会话隔离问题**：每次新对话都需要重新输入背景信息
- **记忆缺失**：AI 无法记住用户的偏好、历史对话、项目信息
- **成本高昂**：重复传输相同上下文导致 API 调用成本激增

### 2. 核心痛点

#### 2.1 企业痛点
| 痛点 | 影响 | 现状 |
|------|------|------|
| **上下文丢失** | 每次对话需重新说明背景，效率低下 | 用户需要反复输入项目信息、技术栈等 |
| **敏感信息泄露** | 数据库密码、API Key 等敏感信息存在泄露风险 | 缺乏自动脱敏机制，依赖人工审查 |
| **跨会话记忆缺失** | 无法延续历史对话，AI 助手"失忆" | 切换设备或新建会话后，AI 不记得之前的内容 |
| **成本控制困难** | 重复传输上下文导致 Token 消耗大 | 每次对话都传输完整历史，成本高昂 |
| **多用户隔离** | 团队协作时，上下文混乱 | 缺乏用户级别的数据隔离 |

#### 2.2 开发者痛点
- **集成复杂**：需要自己实现向量数据库、嵌入模型、检索逻辑
- **维护成本高**：上下文管理涉及存储、检索、安全等多个模块
- **缺乏标准**：各家方案不兼容，迁移成本高

### 2. 核心功能

#### 2.1 智能记忆管理
- **短期记忆**：当前会话的对话历史（最近 N 条消息）
- **长期记忆**：跨会话的重要信息（项目背景、用户偏好、技术栈等）
- **语义检索**：基于向量相似度的智能检索，而非简单关键词匹配

**示例场景：**
```
第一次对话：
用户："我正在开发一个电商系统，使用微服务架构，后端用 Go 语言"
AI："好的，我记住了你的项目信息"

第二天，新会话：
用户："上次讨论的项目用什么技术栈？"
AI："你之前提到在开发电商系统，使用微服务架构，后端是 Go 语言"
```

#### 2.2 敏感信息自动脱敏
- **18 种敏感信息类型检测**：
  - API Key (sk-xxx, api_key_xxx)
  - 数据库密码
  - 手机号、身份证号
  - 邮箱地址
  - IP 地址、域名
  - JWT Token
  - 等等...

- **分层存储**：
  - 原始值加密存储，仅授权人员可访问
  - 日常检索只显示脱敏后的值（如：`sk-****7890`）

**示例场景：**
```
用户："我的 API 密钥是 sk-1234567890abcdefghij"
存储：原始值加密 → vault
检索：显示 "API 密钥: sk-****fghij"
```

#### 2.3 跨会话记忆
- **用户级别隔离**：每个用户有独立的记忆空间
- **工作区关联**：同一项目的不同会话共享上下文
- **时间衰减**：旧记忆自动降低权重，避免过时信息干扰

#### 2.4 MCP 协议支持
- **标准化接口**：符合 Model Context Protocol 标准
- **无缝集成**：支持 Cursor、Claude Desktop、VS Code 等工具
- **插件化扩展**：易于集成到现有 AI 应用

## 🏆 竞争优势

### 1. 技术优势

| 特性 | Context-Keeper | 传统方案 | 优势 |
|------|----------------|----------|------|

| **敏感信息保护** | ✅ 自动检测+分层存储 | ❌ 手动处理 | 降低数据泄露风险 |
| **MCP 协议** | ✅ 原生支持 | ❌ 需要自行适配 | 开箱即用，快速集成 |
| **多维度存储** | ✅ 向量+文件+图谱 | ❌ 单一存储 | 灵活应对不同场景 |
| **用户隔离** | ✅ 原生支持 | ❌ 需要自行实现 | 多租户安全 |
| **本地部署** | ✅ Docker 一键部署 | ❌ 依赖云服务 | 数据主权，成本可控 |

### 2. 成本优势

#### 2.1 降低 API 调用成本
- **传统方案**：每次对话传输完整历史
  ```
  对话 1: 1000 tokens
  对话 2: 1000 + 500 = 1500 tokens
  对话 3: 1500 + 500 = 2000 tokens
  ...
  对话 10: 5500 tokens
  ```

- **Context-Keeper**：只传输相关上下文
  ```
  对话 1: 1000 tokens
  对话 2: 500 + 200 (检索) = 700 tokens
  对话 3: 500 + 200 (检索) = 700 tokens
  ...
  对话 10: 500 + 200 = 700 tokens
  ```

**成本节省：** 10 次对话节省约 **60% Token 消耗**

#### 2.2 本地部署，数据主权
- 无需依赖第三方云服务
- 敏感数据不出企业内网
- 按需扩容，成本可控

### 3. 生态优势
- **开源开放**：MIT 协议，社区驱动
- **标准协议**：MCP 协议，生态兼容
- **插件化架构**：易于扩展和定制

### 2. 手动 API 渗透测试

在自动化扫描基础上，针对业务场景进行了手动攻击模拟。

#### 2.1 认证安全测试

| 攻击类型 | 测试方法 | 系统响应 | 结果 |

#### 2.3 越权访问测试

### 3. 内部安全防御验证

忆安系统内置了敏感信息检测引擎，对以下场景进行了验证。

#### 3.1 敏感信息检测与脱敏

| 测试场景 | 输入内容 | 检出项 | 脱敏效果 | 置信度 |
|---------|---------|-------|---------|--------|
| 患者隐私 | 身份证+手机+银行卡 | 3项 | `110***********1234` / `138****5678` / `6222 **** **** 0123` | 52%-60% |
| API 密钥泄露 | AWS 密钥 AKIA... | 1项 | `[AWS密钥]1234567890ABCDEF` | **98%** |
| 护理对话 | 紧急联系人手机号 | 1项 | `139****2222` | **98%** |
| 多类型混合 | 身份证+手机+银行卡+QQ+邮箱 | 3项 | 身份证/手机/银行卡全部脱敏 | 52%-98% |
| 完整安全扫描 | 身份证+手机+密码 | 2项 | 全部脱敏 | 75% |

#### 3.2 风险评估与响应机制

| 风险等级 | 触发条件 | 系统动作 |
|---------|---------|---------|
| **CRITICAL** (≥80分) | 多种高危敏感信息混合 | **BLOCK 拦截 + ALERT 告警 + REDACT 脱敏** |
| **HIGH** (≥60分) | 单一高危信息或中危+高置信度 | ALERT 告警 + REDACT 脱敏 |
| **MEDIUM** (≥40分) | 中危信息 | REDACT 脱敏 |
| **LOW** (<40分) | 低危信息或无风险 | ALLOW 放行 |

**实测案例**：当输入包含身份证号 + 手机号时，风险评分达 **95/100 (CRITICAL)**，系统自动触发 **BLOCK + ALERT + REDACT 三重响应**。

#### 3.3 Prompt 注入防御

| 测试场景 | 输入内容 | 系统响应 | 结果 |
|---------|---------|---------|------|
| Prompt 注入 + 密码泄露 | "ignore all previous instructions... password: admin123" | 成功检出密码 `admin123`（置信度 90%） | **防御成功** |

## ⚠️ 风险分析与应对

### 1. 技术风险

#### 风险 1：向量检索性能不足
- **影响**：检索速度慢，用户体验差
- **应对**：
  - 采用成熟的向量数据库（Qdrant、Milvus）
  - 建立性能测试基准
  - 提前优化索引策略

#### 风险 2：敏感信息检测误报/漏报
- **影响**：数据泄露或过度脱敏
- **应对**：
  - 建立完善的测试用例库
  - 支持用户自定义规则
  - 提供人工审核机制

### 2. 市场风险

#### 风险 1：大厂推出类似产品
- **影响**：市场份额被挤压
- **应对**：
  - 强化开源社区，建立护城河
  - 专注垂直场景（如代码助手）
  - 提供更灵活的本地部署方案

#### 风险 2：市场需求不足
- **影响**：付费用户增长缓慢
- **应对**：
  - 持续收集用户反馈，快速迭代
  - 降低使用门槛（一键部署）
  - 提供免费版本，培养用户习惯

### 3. 运营风险

#### 风险 1：团队能力不足
- **影响**：产品质量差，进度延期
- **应对**：
  - 招聘有经验的核心团队
  - 建立技术顾问委员会
  - 外包非核心功能

#### 风险 2：资金链断裂
- **影响**：项目无法继续
- **应对**：
  - 控制成本，延长跑道
  - 尽早实现商业化
  - 寻求多轮融资

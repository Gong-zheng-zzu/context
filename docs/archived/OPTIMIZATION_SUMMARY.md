# 🎯 Context-Keeper RAG 检索优化总结

## 项目定位

**Context-Keeper 是一个 RAG（检索增强生成）系统**

```
RAG 工作流程：
用户提问 → 检索相关记忆 → LLM基于检索结果生成回答
         ↑ 本次优化重点
```

---

## 🔍 优化前的问题

### 问题现象
用户问："我是谁？"
- ❌ 系统回答：技术栈信息（Go语言、PostgreSQL、微服务架构）
- ✅ 期望回答：用户名字（宫正行）

### 根本原因
1. **纯语义检索局限** — 只依赖向量相似度，"我是谁"和"电商系统"的语义距离可能很近
2. **无意图理解** — 不知道用户是在问个人信息还是技术信息
3. **结果排序简单** — 只按相似度排序，没有考虑其他因素
4. **内容重复** — 同一条记忆存储多次，占用结果位置

---

## ✨ 已实现的优化

### 1. 混合检索（Hybrid Search）
**语义搜索 + 关键词搜索双引擎**

```go
// 语义搜索（Qdrant向量数据库）
semanticResults := vectorStore.Search(query, topK)

// 关键词搜索（TimescaleDB时序数据库）
keywordResults := timeStore.SearchByKeyword(keywords, topK)

// 结果合并 + 关键词匹配加成
mergedResults := mergeAndBoost(semanticResults, keywordResults)
```

**效果**：
- 语义搜索：理解"我是谁"的语义
- 关键词搜索：精确匹配"宫正行"、"姓名"等关键词
- 双重保障，提高召回率

---

### 2. LLM 意图分析
**使用 qwen2.5:7b 分析查询意图**

```go
// 分析用户查询意图
intent := llm.AnalyzeIntent(query)
// 返回：
// - type: "personal_info" | "technical" | "project" | "general"
// - keywords: ["姓名", "身份", "个人"]
// - entities: ["宫正行"]
```

**效果**：
- 识别查询类型（个人信息 vs 技术信息）
- 提取关键词用于关键词搜索
- 指导后续的重排序策略

---

### 3. 智能重排序（Reranking）
**多因素加权排序**

```go
finalScore = 
    semanticScore * 0.5 +      // 语义相似度
    keywordScore * 0.3 +       // 关键词匹配度
    recencyScore * 0.1 +       // 时间新鲜度
    entityScore * 0.1          // 实体匹配度

// 特殊加成
if (hasAnswer && !isQuestionOnly) {
    finalScore *= 1.5  // 包含答案的记忆提升50%
}
if (isPersonalQuery && hasEntity) {
    finalScore *= 1.3  // 个人信息查询且包含实体提升30%
}
```

**效果**：
- 过滤掉"只是问题"的记忆（如"我是谁？"本身）
- 提升包含答案的记忆（如"我的名字是宫正行"）
- 综合多个维度，而非单一相似度

---

### 4. 内容级去重
**ID去重 + 内容指纹去重**

```go
// ID去重（防止同一记忆被检索多次）
seenID := make(map[string]bool)

// 内容去重（防止相同内容不同ID的重复）
contentKey := content[:min(200, len(content))]
seenContent := make(map[string]bool)
```

**效果**：
- 优化前："电商系统..."出现4次
- 优化后："电商系统..."只出现1次
- 结果多样性提升，更多不同内容

---

### 5. TimescaleDB 双写
**存储时同时写入向量库和时序库**

```go
// 存储到Qdrant（语义搜索）
vectorStore.Store(memory)

// 存储到TimescaleDB（关键词搜索 + 时间线）
timeStore.Store(memory)
```

**效果**：
- 支持混合检索
- 支持时间线查询
- 数据冗余备份
